# Exercise 3.5

## Question

Why is it not feasible in general for function types to be instances of the Eq class? When is it feasible?

*Hint*: two functions of the same type are equal if they always return equal results for equal arguments.

## Solution

Given that two functions of the same type signature are equal iff they return equal results for all equal inputs, it is generally not feasible to make function types instances of the `Eq` class, for several reasons:

1. **Infinite Domains**  
   Many input types (e.g., Int, String, [a]) have infinitely many possible values. To determine whether two functions are equal, one would have to compare their results for every possible input, which is not computationally feasible.
2. **Undecidability**  
   Function equality is undecidable *in general*. Determining whether two arbitrary functions behave identically for all inputs is equivalent to solving the Halting Problem, which is provably impossible.
3. **Opacity of functions**  
   In Haskell, functions are opaque at runtime: there is no way to inspect or deconstruct their internal structure. This is why Eq cannot be implemented for general functions: the runtime system cannot tell whether two functions are equal by just looking at their closures.
4. **Side Effects and Partiality**  
   Functions may be partial (i.e., undefined for some inputs) or involve side effects (e.g., through IO). These aspects further complicate attempts to define equality.

However, it is feasible for function types to be instances of the `Eq` class in restricted cases:

1. **Finite Domain**  
   If the input type has a small, finite number of possible values (e.g., Bool, Maybe ()), equality can be determined by exhaustively evaluating both functions on all inputs and comparing the results.
2. **Symbolic Representation (e.g., DSLs)**  
   When functions are represented as symbolic expressions (such as abstract syntax trees in a domain-specific language (DSL)) it becomes possible to define structural equality. Two such symbolic functions can be compared based on their structure rather than their runtime behavior.  
   An example is the arithmetic expression DSL discussed in Chapter 17 of this book, where two expressions can be compared structurally.
