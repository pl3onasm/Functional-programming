# Exercise 6.51

In the previous exercises, we have defined a number of functions for a supermarkt billing system. The question now is: how appropriate would it be to test this system using QuickCheck? Could we check parts of the system using QuickCheck? Could we use it to test the entire system? Or could we do both?

This question forces us to think about what QuickCheck is good at and what it is not. QuickCheck is particularly well-suited for testing properties of pure functions (i.e., functions without side effects). These are expressed as laws, invariants, or relationships that should hold true for all possible inputs.

In the context of our supermarket billing system, we can identify several pure functions having clear algebraic properties that could be tested using QuickCheck. Here are some examples of properties we could test:

1. **Database Lookup**
   - look db code: should never return a price less than 0.
   - addItem: adding an item to the database and then looking up its barcode, should return the newly added item as a tuple (name, price).
   - removeItem: removing an item from the database and then looking up its barcode, should return ("Unknown Item", 0).

2. **Bill Calculation**
   - makeTotal: should equal the sum of the prices of all items in the bill.
   - adding an unknown item to the bill should not change the total.
   - makeBill: should never contain "unknown item" since these are filtered out.

3. **Formatting invariants**
   - formatLine: every line from formatLine should have length equal to lineLength.
   - formatPence should always contain exactly one decimal point and two digits after it.

However, the entire system, taken as a whole, is about producing human-readable output (formatted bills). Testing this aesthetic output directly is not well suited for QuickCheck. While we can check that the total amount in the formatted bill matches the sum of the item prices, verifying the exact layout and formatting of the bill is more subjective and less about functional correctness. QuickCheck is all about properties that hold for all inputs: it generates random inputs and looks for invariant properties, not specific output formats. A better approach for testing the latter would be to use example-based unit tests, such as golden file tests, where we compare the program’s output for a fixed input against a stored reference output.

In summary, QuickCheck is very appropriate for testing individual parts of the system with universal properties. It is not appropriate for testing the whole system end-to-end, especially when the output is more about presentation than functional correctness. The best approach is to use QuickCheck to test invariants of pure functions, and golden file tests for fixed examples of formatted bills.
