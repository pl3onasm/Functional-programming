# Exercise 6.20

Earlier we represented pictures as a list of rows of characters. Redefining `Picture` as a list of columns of characters, would not change the data shape: it would still be a list of lists of characters. However, it would change the semantics: each inner string would now represent a column, not a row. That means that the functions would have to be rethought to reflect this new meaning.

## Vertical Flip

In row-based representation, `flipV` reversed the elements inside each row to achieve a flip in a vertical mirror. In column-based representation, `flipV` would reverse the order of the columns themselves.

```haskell
flipV :: Picture -> Picture
flipV pic = reverse
```

## Horizontal Flip

In row-based representation, `flipH` reversed the order of the rows to produce a flip in a horizontal mirror. In column-based representation, `flipH` would reverse the elements inside each column.

```haskell
flipH :: Picture -> Picture
flipH pic = [reverse col | col <- pic]
```

## Beside

In row-based representation, `beside` put two pictures next to each other by concatenating the corresponding rows using zip. In column-based representation, `beside` would concatenate the two lists of columns.

```haskell
beside :: Picture -> Picture -> Picture
beside pic1 pic2 = pic1 ++ pic2
```

## Above

In row-based representation, `above` put one picture above another by concatenating the two lists of rows. In column-based representation, `above` would concatenate the corresponding columns using zip.

```haskell
above :: Picture -> Picture -> Picture
above pic1 pic2 = [col1 ++ col2 | (col1, col2) <- zip pic1 pic2]
```

## Rotate

In row-based representation, the function `rotate` achieves a 180-degree rotation by first horizontally flipping the picture and then vertically flipping it. In column-based representation, the same logic and implementation would apply: it is still defined as a composition of `flipH` and `flipV`, but these functions have different implementations as shown above. The same applies to `rotate90` and `rotateMin90`.

## Scale

Just as was the case with the rotation functions, the `scale` function would remain unchanged in its definition. Replacing each element with a block of the same element would still work as intended, regardless of whether the picture is represented as rows or columns.

## Conclusion

The functions `flipV`, `flipH`, `beside`, and `above` change as expected to reflect the new column-based representation: `flipV` is now implemented as `flipH` was for the row-based representation, and vice versa. The `beside` and `above` functions also swap their implementations accordingly.

Another way to define these functions is to just transpose the picture at the beginning and end of each function, effectively converting between row-based and column-based representations as needed. This approach would allow us to reuse the original implementations of these functions without modification. However, this would also introduce additional overhead.
